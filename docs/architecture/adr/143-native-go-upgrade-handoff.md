# 原生 Go 稳定宿主与在线迁移

## 背景

原生 Go 进程需要从 GitHub 正式版更新，且实例的 API、管理地址、会话和用户数据需要跨版本保留。运行中的 Windows 可执行文件和 Linux 监听描述符有不同生命周期。数据库连接、定时任务、消息消费者和上传暂存使用的锁也各有所有者。升级协议必须约束这些资源移交的时点。

## 决定

在 Windows amd64、Linux amd64 和 Linux arm64 使用独立的 `clouddrive-host` 持有 Go 的原业务和管理端口。使用 Go 标准库的 HTTP 反向代理，在同一连接入口切换私有业务进程。Linux 采用 Unix socket、进程组和文件权限，Windows 采用带 ACL 的命名管道与 Job Object。每一版本使用单独目录，复用 Sigstore TUF、GitHub OIDC 签名和项目已有数据库迁移契约。

旧进程继续接收业务，候选读取配置和数据库兼容信息后回报 `prepared`。有在线迁移时，旧版认可签名的扩展契约，宿主登记恢复点后，候选才可执行受限的增量 DDL。随后宿主暂停准入并等待在途请求结束，旧版停掉后台消费者并释放实例租约，候选取得租约、启动私有 HTTP 后回报 `active-ready`。宿主提交版本决策，开启新进程的业务准入，再让旧进程退出。

切换预算为 5 秒，最多等待 128 个新请求。已经转发的请求由原进程完成。排空失败时恢复旧版准入，超出队列容量或等待预算的请求收到带 `Retry-After` 的 503。SQLite、PostgreSQL 和 MySQL 使用各自的迁移原子性与互斥机制，允许旧版在明示兼容的扩展 schema 上重新取得所有权。

## 后果与退出条件

现有原生实例首次交由宿主监听时，需要有计划地交还原端口。切换后的业务二进制可以回退至签名契约准许的上一个版本，数据库与已确认的写入随实例保留。需要回收字段、重写存量数据、升级宿主本身或跨主机运行时，另行验证迁移与运行时方案。容器及配套 Web Host 沿用各自的发布机制，容器宿主维护的决定见[同址宿主维护与完整恢复点](142-host-maintenance-gateway.md)。
